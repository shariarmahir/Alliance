# AutoLink Integrated Technologies — Project Guide

AutoLink Integrated Technologies (brand wordmark: "AutoLink") is a premium B2B
e-commerce storefront for industrial electronics (PLCs, inverters, servos, motors,
power system electronics, factory/garment automation parts), based in Bangladesh but
built to be sold and shipped internationally. UI/UX is cloned from Radwell
(radwell.co.uk) for the landing page, product listing, and product detail screens.
This is a **quotation-based B2B flow**, not a cart/checkout store: there is no
"Add to Cart" — customers request a quotation, confirm an order from that quote, and
track delivery.

Alongside the storefront sits a full **Super Admin / Sub-Admin dashboard** for running
the business: catalog management, order/quotation operations, employee/task/leave
management, and analytics.

## Stack

- Next.js 16 (App Router, Turbopack), React 19, TypeScript
- Tailwind CSS v4 (`@theme` tokens in `app/globals.css`, no `tailwind.config.js`)
- shadcn/ui components (Base UI primitives, not Radix) in `app/components/ui/`
- Recharts for admin analytics charts
- No external database — persistence is JSON files under `data/`, read/written via
  server-only modules. No FastAPI/Python backend exists; `Allaince-backend/` (sibling
  folder, one level up) is currently empty. Everything runs through Next.js Route
  Handlers.

**Read `node_modules/next/dist/docs/` before writing App Router code that touches
routing, layouts, or server/client boundaries** — this Next.js version has breaking
changes from what you may expect (`middleware.ts` is renamed `proxy.ts`, for example).
See `AGENTS.md` for the enforcement note; that file is regenerated by `next dev` and
should be committed as-is, not hand-edited.

## Conventions (non-negotiable, per project owner)

- **No `src/` folder.** Everything lives directly under `app/`.
- **One file per route: `page.tsx`.** Route logic and markup live in `page.tsx`
  (server component) with a `*-client.tsx` sibling only when interactivity requires
  `"use client"`. Don't fragment a single screen across unnecessary extra files.
- **Global CSS only.** All styling is Tailwind utility classes plus the tokens/utilities
  in `app/globals.css` (see `.btn-glass`, `.btn-glass-accent`, `.glass-panel`). No
  per-page CSS Modules, no styled-components, no inline `<style>` blocks.
- **Short, direct code.** No speculative abstractions, no unused config toggles, no
  defensive code for cases that can't occur server-side. Prefer three similar lines
  over a premature helper.
- Server-only data access (`fs`/`fs/promises`) is isolated behind modules that
  `import "server-only"` at the top — never imported into a `"use client"` file
  directly. If a client component needs that data, the server component (`page.tsx`)
  fetches it and passes it down as a prop. See "Data Layer" below.

## Route Map

### Storefront (`app/(site)/`)

| Route | Purpose |
|---|---|
| `/` | Landing page: hero carousel, category grid, top sellers, services, brand strip, client reviews, "We Are Here To Help You" contact panel |
| `/products` | Product listing with category/brand filters (Radwell-style) |
| `/products/[slug]` | Product detail — spec table, gallery, **"Request Quotation"** button (not Add to Cart) |
| `/quote` | Quotation cart — quantities/pricing for all requested items, submits to `/api/quotations` |
| `/order/confirm` | Delivery options + date picker after a quotation is accepted |
| `/order/success` | Order number, tracking ID/link, invoice download (jsPDF) and print |
| `/track/[trackingId]` | Live delivery tracking timeline |
| `/contact` | Real contact form, posts to `/api/contact` |

### Admin (`app/admin/`)

Auth-gated by `proxy.ts` (this Next version's renamed `middleware.ts`). Session cookie
is `autolink_admin_session`, parsed by `parseAdminSession()` in `app/lib/admin-auth.ts`.
Shape: `{ role: "super" | "sub", name, email, employeeId? }`.

- `/admin/login` — credential form (see Auth & Accounts below)
- `/admin` — role-branched: super admin sees the analytics Overview; sub-admin sees
  their personal dashboard (`sub-admin-dashboard.tsx`)
- Super-admin-only: `/admin/orders`, `/admin/quotations`, `/admin/contact-requests`,
  `/admin/emails`, `/admin/employees`
- Shared (super + sub, per RBAC below): `/admin/products`, `/admin/stock`,
  `/admin/hero-images`, `/admin/tasks`, `/admin/leave`, `/admin/daily-report`

**RBAC is enforced in two places, deliberately:**
1. `proxy.ts` — route-level. `SUB_ADMIN_ALLOWED_PREFIXES` (prefix match) plus a
   separate `SUB_ADMIN_ALLOWED_EXACT = ["/admin"]` (exact match only — `/admin` must
   never become a prefix match, or it would swallow every other `/admin/*` super-only
   route). If you add a new sub-admin-accessible route, add it to the prefix list; if
   you add a new super-only route, add nothing — it's blocked by default.
2. Per-resource ownership inside route handlers — e.g. a sub-admin can `PATCH` their
   own task's status but gets `403` on another employee's task, checked by comparing
   `session.employeeId` against the resource's owning employee ID. RBAC alone isn't
   enough for employee-scoped data; always check ownership too.

## Data Layer

No database. Persistence is JSON files in `data/` at the repo root of
`Alliance-frontend/`, read/written via `fs`/`fs/promises` in server-only modules —
**no module-level caching**, every read hits disk so admin mutations are immediately
visible.

| File | Module | Covers |
|---|---|---|
| `products.json`, `categories.json` | `app/lib/admin-catalog.ts` | Catalog, stock, bulk import |
| `orders.json`, `quotations.json`, `contact-requests.json`, `emails.json` | `app/lib/admin-operations.ts` | Operations |
| `employees.json`, `tasks.json`, `leave-requests.json`, `daily-reports.json` | `app/lib/admin-employees.ts` | Employee system |
| `hero-images.json` | — | Hero carousel image control |

Products/categories/reviews/FAQ that aren't yet admin-editable still live as arrays in
`app/lib/mock-data.ts` (itself `server-only`, seeded from `data/*.json` where
applicable). **These are mock/seed values — replace with real product data before
production**, per the original project brief.

`app/lib/mock-analytics.ts` holds generated chart data for the admin dashboards
(revenue, order ratio, traffic, etc.) — also mock, not derived from real orders yet.

### Server-only import boundary (recurring gotcha)

Any module with `import "server-only"` (all of the `admin-*.ts` files, `mock-data.ts`)
can **only** be imported by server components. If a component needs `"use client"`
(state, refs, event handlers, effects), it must not import those modules directly —
split into a server component that fetches the data and a client child that receives
it as a prop. Example: `app/components/client-reviews.tsx` (server, imports
`mock-data.ts`) renders `app/components/client-reviews-carousel.tsx` (`"use client"`,
takes `reviews` as a prop). Get this wrong and the build fails with *"You're importing
a module that depends on 'server-only' into a React Client Component module."*

### `useSearchParams()` requires Suspense

Next's static prerendering fails at **build time only** (not caught by `tsc` or
`eslint`) if a page calls `useSearchParams()` without a `<Suspense>` boundary above it.
Pattern used in `app/(site)/order/success/page.tsx`: thin default-export wrapper
renders `<Suspense fallback={null}><PageContent /></Suspense>`, and the component
calling `useSearchParams()` is the inner `PageContent`, not the export. Always run a
real `npm run build` before pushing — `tsc --noEmit` and `next lint` both pass while
this error still breaks production/Vercel deploys.

## Category & Brand Cards (design pattern)

`app/components/category-grid.tsx` and `app/components/brand-strip.tsx` use a small
rotating palette of Tailwind gradient/ring theme objects (indexed by array position,
`% themes.length`) to give each card a distinct hover treatment without needing
per-category background images or external assets. Follow this pattern rather than
sourcing/hardcoding photography for new card grids.

## Working Directory Gotcha

`package.json` lives in `Alliance-frontend/`, **not** the repo root
(`M:\Private projects\Alliance\`). Always `cd` into `Alliance-frontend` before running
`npm run dev`, `npm run build`, etc. — running them from the repo root fails with
`ENOENT: no such file or directory, open 'package.json'`. The same root-folder
mismatch was the cause of an early Vercel deployment 404: the Vercel project's **Root
Directory** setting must be `Alliance-frontend`, or Vercel builds from the repo root
and finds no app.

## Naming History

The product was renamed from "Alliance" to "AutoLink Integrated Technologies"
(wordmark: "AutoLink") mid-build. Everything user-facing and every internal identifier
was updated at that point:
- Session cookie: `alliance_admin_session` → `autolink_admin_session`
- localStorage keys: `alliance_order`/`alliance_quote`/`alliance_quotation` →
  `autolink_order`/`autolink_quote`/`autolink_quotation`
- Contact email: `info@alliance.com` → `info@autolink.com`
- `package.json` name: `alliance-frontend` → `autolink-frontend`

**What was deliberately left unchanged:** the repo root folder (`Alliance/`), the
`Alliance-frontend/` app folder itself, and the GitHub remote
(`github.com/shariarmahir/Alliance.git`) — renaming those is a filesystem/git-remote
operation with real risk (breaks the working directory path, local clones, CI/deploy
hooks pointed at the old remote name) and hasn't been requested. Don't assume the repo
folder name reflects the current brand. Also left alone: any pre-existing mock data
referencing unrelated third-party company names (e.g. a vendor called "Alliance
Freight Forwarders" in `data/emails.json`'s sample inbox) — that's a different
business, not this one, and renaming it would be a data-accuracy bug, not a fix.
